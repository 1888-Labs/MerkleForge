Faster than what?

Measured 2026-11-06 for MerkleForge 0.5.2 (i7-1185G7, 4 cores / 8 threads, rustc 1.97.1), SHA-256 everywhere, the same 32-byte leaves for every library, Criterion medians. Every ratio is MerkleForge against the named library, same operation, same leaves, same hash, same run. The libraries produce different roots (MerkleForge domain-separates leaves and nodes), so this compares speed for the same job, not identical output.

Against merkle_light at 1,048,576 leaves, MerkleForge builds 2.7x faster and verifies 10,000 proofs 3.7x faster with parallel; single-threaded, the two are within about 20% on every operation. merkle_light has no multiproofs.

What favours whom:

  • MerkleForge hashes every leaf with a 0x00 prefix and every node with a 0x01 prefix, which blocks second-preimage attacks. That is extra work the other libraries skip, and it is counted in MerkleForge's times.
  • rs-merkle is given its leaves already hashed in verification (its API takes leaf hashes); MerkleForge hashes the raw leaf inside verify. In construction, rs-merkle's leaf hashing is timed.
  • Rows marked 8 threads use the parallel feature (rayon) on this 4-core laptop; the other libraries have no multi-threaded build or batch verifier. The one-thread rows are the like-for-like comparison.

Faster than what?

Every TypeScript speed ratio names its baseline. There are three, and they are never mixed:

BaselineWhat is comparedHeadline (131,072 leaves)

There is no speed claim against the Rust crates. The TypeScript packages are a port of them and are checked against them for identical output, not raced against them.

Parity: same bytes first

A speedup only counts if the output is the same. bench/parity.mjs builds the benchmark's own trees (the same leaves that are timed) and compares the output byte for byte with OpenZeppelin, @noble/hashes, and the Rust crates, which it runs live. It runs in CI on every pull request and fails the build on any difference.

The unit tests add property tests against the real @openzeppelin/merkle-tree (150 random trees per tree type, random leaf types, values, and sizes), test vectors generated by the Rust crates for every tree, proof, multiproof, and codec (serde_json and bincode), and the Solidity verifiers checked with Foundry against fixtures produced by the TypeScript packages.

  • BinaryMerkleTree with @merkleforge/hash-wasm builds a Keccak-256 tree about 10x faster than merkletreejs and 100x faster than OpenZeppelin, even though it hashes every leaf with a domain prefix (H(0x00 ‖ leaf), which blocks second-preimage attacks): twice the hashing of merkletreejs, which uses leaves as nodes directly.
  • With pure-JavaScript Keccak it is 1.5x faster than merkletreejs.
  • @merkleforge/openzeppelin produces the same roots and proofs as @openzeppelin/merkle-tree while building trees 8–15x faster, generating proofs 4–6x faster, and verifying them 4–5x faster.
  • The Aztec trees use LMDB storage and, in some runs, Poseidon2, so they are not like for like.

Measured on MerkleForge 0.2.3, Node.js 24.15, i7-1185G7, 2026-11-01. Per-size tables, the exact method, every caveat, and where each claim in the READMEs comes from are in BENCHMARKS.md.
