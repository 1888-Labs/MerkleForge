Benchmarks

The Rust crates and the TypeScript packages are benchmarked separately, each with its own harness. Lower latency is better; higher throughput is better. Results are hardware-specific: compare trends across machines, not absolute values.

Showing code for

MerkleForge uses Criterion benchmarks in the unpublished merkle-bench crate to compare hash adapters, tree variants, proof generation, proof verification, and other Rust Merkle libraries. Criterion reports mean, median, and standard deviation to filter out noise. For the latest CI numbers with links to every Criterion report, see the live benchmark explorer.

The tables below are copied from BENCHMARKS.md (run date 2026-08-17). That run predates the v0.5.0 sparse-tree and Patricia-trie performance fixes, which cut 4,000 sequential sparse inserts from about 223 s to 0.2 s and 4,000 Patricia inserts from about 5.9 s to 0.02 s. Sparse and Patricia numbers here are therefore pessimistic. Cells marked not captured were not completed in that run. The comparison with rs-merkle and merkle_light was rerun on 2026-11-06 for 0.5.2.

The TypeScript packages are compared with other JavaScript Merkle tree libraries: @openzeppelin/merkle-tree, merkletreejs, @aztec/merkle-tree, and @aztec/world-state. The suite lives in bench/ in the MerkleForge-ts repository. All numbers come from one run on one machine, so read them as ratios, not absolutes. The same results are on the benchmarks page.

The tables below are copied from BENCHMARKS.md in the MerkleForge-ts repository (MerkleForge 0.2.3, run date 2026-11-01).

What favours whom:

  • MerkleForge hashes every leaf with a 0x00 prefix and every node with a 0x01 prefix, which blocks second-preimage attacks. That is extra work the other libraries skip, and it is counted in MerkleForge's times.
  • rs-merkle is given its leaves already hashed in verification (its API takes leaf hashes); MerkleForge hashes the raw leaf inside verify. In construction, rs-merkle's leaf hashing is timed.
  • Rows marked 8 threads use the parallel feature (rayon) on this 4-core laptop; the other libraries have no multi-threaded build or batch verifier. The one-thread rows are the like-for-like comparison.

Parity: same bytes first

The Rust crates are the reference implementation. The TypeScript packages are checked against them byte for byte, live, in the TypeScript repository's CI: roots and the bincode bytes of every sampled proof for Keccak-256 and SHA-256 trees of up to 131,072 leaves, plus generated test vectors for every tree, proof, and codec. Switch to TypeScript above for the full table.

What is measured

Each table below names the Criterion benchmark that produced it. Latency is the time for one operation; construction builds a fresh tree from the given number of leaves.

Each library builds a tree from the same random 32-byte leaves, generates proofs for the same 2,000 random leaves, and verifies every proof (a run fails if any proof does not verify). Build time is the median of 3 builds; proof and verify times are the mean per operation after a warm-up. Database setup (Aztec) is not counted.

Sizes are powers of two, so the fixed-depth Aztec trees are full and have the same depth as the other trees, except @aztec/world-state, whose note hash tree is always 42 levels deep.

What differs between libraries, so the numbers are not like for like:

  • Hash. OpenZeppelin, merkletreejs, and one Aztec StandardTree run use Keccak-256 from @noble/hashes; MerkleForge uses its own pure-JS Keccak-256 (identical digests, see Parity) or WebAssembly where noted. The other Aztec runs use Poseidon2, a SNARK-friendly hash that costs more per call in JavaScript.
  • Storage. The Aztec trees keep nodes in LMDB and support commit, rollback, and snapshots. @aztec/world-state is Aztec's native C++ rollup state. The other libraries keep the tree in memory.
  • Verification. OpenZeppelin, merkletreejs, and MerkleForge verify with their own functions. The Aztec trees have no verifier on the tree, so their proofs are checked with Aztec's computeRootFromSiblingPath and Aztec's synchronous Poseidon2. For world-state that means 42 Poseidon2 hashes in JavaScript per proof, which is why its verify column is high.
  • Proof generation in the OpenZeppelin-compatible trees re-verifies every proof before returning it (both libraries do this), so it is slower than in BinaryMerkleTree.
  • Leaf hashing. BinaryMerkleTree hashes every leaf with a domain prefix (H(0x00 || leaf)), which protects against second-preimage attacks. That is twice the hashing of merkletreejs, which uses leaves as nodes directly.

Reading the tables

  • Latency: time for one operation.
  • Throughput: bytes or elements processed per second.
  • Proof generation: time to produce the witness sent to a verifier.
  • Proof verification: time for a stateless client to check the witness against a trusted root.
  • Proof size: bytes sent over the network or stored as evidence.
