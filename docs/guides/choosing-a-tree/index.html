Choosing a tree

MerkleForge ships three tree variants. They share the MerkleTree<H> traitMerkleTree interface but are built for different shapes of data.

Quick decision guide

  • You have a list and prove items by position: use BinaryMerkleTree. It has the smallest proofs and the fastest construction.
  • You have a key-value map and need to prove a key is absent: use SparseMerkleTree. Keys are 32 bytes, so hash longer keys first.
  • You need roots or witnesses that Ethereum tooling understands: use MerklePatriciaTrie<Keccak256>.

Writing code that works with any variant

The shared traitinterface lets you write generic code. Each variant also has a native API (keys for the sparse tree and trie); the traitinterface maps leaf indices onto it.

use merkle_core::prelude::*;
use merkle_variants::{BinaryMerkleTree, MerklePatriciaTrie, SparseMerkleTree};
use merkleforge_hash::Sha256;
 
/// Insert rows through the shared trait and return a metadata snapshot.
fn commit<H, T>(tree: &mut T, rows: &[&[u8]]) -> Result<TreeMetadata, MerkleError>
where
    H: HashFunction,
    T: MerkleTree<H>,
{
    for row in rows {
        tree.insert(row)?;
    }
    Ok(tree.metadata())
}
 
fn main() -> Result<(), MerkleError> {
    let rows: &[&[u8]] = &[b"alice:100", b"bob:250", b"carol:75"];
 
    let binary = commit(&mut BinaryMerkleTree::<Sha256>::new(), rows)?;
    let sparse = commit(&mut SparseMerkleTree::<Sha256>::new(), rows)?;
    let trie = commit(&mut MerklePatriciaTrie::<Sha256>::new(), rows)?;
 
    for meta in [binary, sparse, trie] {
        println!("{:<18} leaves={} height={}", meta.variant, meta.leaf_count, meta.height);
    }
    Ok(())
}

The sparse tree and trie implement MerkleTree through an indexed() view that shares the tree's state:

import { type Bytes, type MerkleTree, type TreeMetadata, utf8 } from '@merkleforge/core'
import { Sha256 } from '@merkleforge/hash'
import { BinaryMerkleTree, MerklePatriciaTrie, SparseMerkleTree } from '@merkleforge/variants'
 
/** Insert rows through the shared interface and return a metadata snapshot. */
function commit(tree: MerkleTree, rows: Bytes[]): TreeMetadata {
  for (const row of rows) tree.insert(row)
  return tree.metadata()
}
 
const rows = ['alice:100', 'bob:250', 'carol:75'].map(utf8)
 
const binary = commit(new BinaryMerkleTree(Sha256), rows)
const sparse = commit(new SparseMerkleTree(Sha256).indexed(), rows)
const trie = commit(new MerklePatriciaTrie(Sha256).indexed(), rows)
 
for (const meta of [binary, sparse, trie]) {
  console.log(`${meta.variant.padEnd(18)} leaves=${meta.leafCount} height=${meta.height}`)
}

How the shared interface maps onto each variant

  • Binary: insert appends and returns the next index. remove replaces the leaf with H::empty()hasher.empty(); later indices are unchanged.
  • Sparse: leaf index i is stored at a key whose last 8 bytes are i in big-endian order. insert returns the first unoccupied index at or above the leaf count, so it never overwrites a leaf after a removal. generate_proofgenerateProof returns a MerkleProof with 256 path nodes.
  • Patricia: leaf index i is stored under the key merkleforge:mpt:trait-leaf: ‖ i (8 bytes, big-endian). generate_proof through the trait returns MerkleError::UnsupportedOperationgenerateProof through the view throws MerkleError with code 'UnsupportedOperation', because Patricia proofs are key-addressed. Use MerklePatriciaTrie::generate_proof(key)trie.generateProof(key) instead.

Use the traitinterface for generic plumbing (ingestion, metadata, benchmarks). Use each variant's native API when you need key-addressed proofs.
